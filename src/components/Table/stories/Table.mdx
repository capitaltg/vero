# Table

> **Experimental.** Both components are exported for early feedback. They are complete and covered
> by tests, but the API may change, or they may be removed, without a major version bump. Each
> export is tagged `@experimental`, and the first table to mount logs a one-time warning in
> development builds. See the [Table plan](https://github.com/capitaltg/vero/blob/main/src/components/Table/PLAN.md)
> for status.

Accessible, 508-friendly tables styled after the
[USWDS Table](https://designsystem.digital.gov/components/table/), with sorting, column grouping
and responsive behavior built on [TanStack Table](https://tanstack.com/table).

Vero ships two components over one render layer:

<DocsSubheading id="when-to-use">When to use</DocsSubheading>

- **For data people compare across rows and columns**, such as statistics, budgets or case
  counts.
- **For directories**: lists of people, offices or resources where every item has the same
  fields.

<DocsSubheading id="when-to-use-something-else">When to use something else</DocsSubheading>

- **Data that isn't tabular:** use a list, or a description list (`<dl>`) for label and value
  pairs.
- **Trends and relationships:** a chart may show them more clearly. A table of the same data is
  still a useful alternative to the chart.
- **Page layout:** don't use a table to lay out a page or a dashboard. Use CSS grid or flexbox.
- **Long text:** keep cells short. Content that runs to paragraphs belongs under headings or in
  an [Accordion](?path=/docs/data-display-accordion--docs).
- **Items with different fields:** use a list or cards.

<DocsSubheading id="usability">Usability guidance</DocsSubheading>

- **Keep it plain.** The default bordered style is enough. Extra decoration makes data harder to
  scan.
- **Always have a header row**, with short labels that say what each column holds. When one
  column identifies each row, such as a name, make it the row header (`meta.isRowHeader`, or
  `<TableHead scope="row">`).
- **Keep each column consistent.** Use one unit and one format per column, so values compare
  easily. Put the unit in the header, such as "Salary (USD)", rather than in every cell.
- **Right-align numbers** (`meta: { align: 'right' }`, or `text-right` on the primitives) so the
  digits line up. For amounts, percentages and counts, add `tabular-nums` so every digit has the
  same width. Phone numbers, ZIP codes and dates don't need either.
- **Say where the data comes from.** Put the source and the last-updated date in the caption,
  especially for data that changes often.
- **Plan for small screens.** Any table with more than two columns needs a narrow-screen plan.
  The default horizontal scroll suits numeric tables with many columns; `responsive="stack"`
  suits directories and record-style data. See [Responsive behavior](#responsive-behavior).
- **Use as few columns as you can.** People scan down a column more easily than across a row.
  Drop columns people don't need, or swap rows and columns.
- **Sort long tables** when the order matters to people, such as alphabetical or by amount.
  Don't count on sorting in a stacked table: the header row and its sort buttons are hidden while
  the table is stacked.

</DocsSection>

## Quick start

```tsx
import { Table, TableBody, TableCell, TableHead, TableHeader, TableRow } from '@capitaltg/vero';

<Table caption="Quarterly revenue">
  <TableHeader>
    <TableRow>
      <TableHead scope="col">Quarter</TableHead>
      <TableHead scope="col">Revenue</TableHead>
    </TableRow>
  </TableHeader>
  <TableBody>
    <TableRow>
      <TableHead scope="row">Q1</TableHead>
      <TableCell>$1.2M</TableCell>
    </TableRow>
  </TableBody>
</Table>;
```

The `caption` prop is a convenience for the common case; compose `<TableCaption>` yourself when
the caption needs its own markup.

The same table, config driven:

```tsx
import { DataTable, type DataTableColumnDef } from '@capitaltg/vero';

interface Person {
  name: string;
  role: string;
  salary: number;
}

const columns: DataTableColumnDef<Person>[] = [
  // One column per table should be the row header.
  { accessorKey: 'name', header: 'Name', meta: { isRowHeader: true } },
  { accessorKey: 'role', header: 'Role' },
  {
    accessorKey: 'salary',
    header: 'Salary',
    meta: { align: 'right' },
    cell: info => `$${info.getValue<number>().toLocaleString()}`,
  },
];

<DataTable caption="Team roster" columns={columns} data={people} />;
```

Every table needs an accessible name. Prefer a visible `caption`; if a heading beside the table
already names it, pass `captionHidden` to keep the caption for screen readers only, or use
`aria-label`.

## `Table` props

<Controls of={TableStories.Playground} />

Alongside `caption` / `captionHidden`, `Table` takes the styling and responsive props shared with
`DataTable`: `variant` (`bordered` | `borderless`), `striped`, `density` (`default` | `compact`),
`stickyHeader`, `responsive` (`scroll` | `stack` | `none`), `stackBreakpoint` (`sm` | `md` | `lg`)
and `stackedStyle` (`default` | `headers`). Everything else lands on the `<table>` element.

The children are thin wrappers over the native elements: `TableCaption` (`<caption>`, with
`hidden` for a screen-reader-only caption), `TableHeader` (`<thead>`), `TableBody` (`<tbody>` —
use several for row-group sections), `TableFooter` (`<tfoot>`), `TableRow` (`<tr>`), `TableHead`
(`<th>`, with `scope` defaulting to `col`) and `TableCell` (`<td>`). Both cell components accept a
`label`, shown above the value while the table is stacked. The [API reference](#api-reference) at
the end of this page lists the props of `Table`, `TableCaption`, `TableHead` and `TableCell`.

Type your column array as `DataTableColumnDef<T>[]` (exported from Vero) to get autocomplete and
typo checking on these fields. Plain TanStack `ColumnDef` arrays and `createColumnHelper` output
are accepted too, just without that checking on `meta`.

Vero deliberately doesn't add these fields to TanStack's global `ColumnMeta` type: that would
change the types of every app that imports Vero, and break apps that already define a field such
as `align` of their own. If you'd rather have them on `ColumnMeta` everywhere, for example to use
`createColumnHelper` with full checking, opt in from your own app:

```ts
import type { DataTableColumnMeta } from '@capitaltg/vero';
import type { RowData } from '@tanstack/react-table';

declare module '@tanstack/react-table' {
  interface ColumnMeta<TData extends RowData, TValue> extends DataTableColumnMeta {}
}
```

## Responsive behavior

This is the part you get for free, and it works the same on both components.

### Scrolling — the default

Wide tables get a horizontal scroll container. It only becomes a focusable, labeled
`role="region"` when the content actually overflows, so a table that fits never adds a stray tab
stop, and one that doesn't fit stays reachable by keyboard.

<Canvas of={DataTableStories.Scrollable} />

Unlike USWDS we don't force `white-space: nowrap` on cells, so text wraps by default and narrow
tables simply get narrower. Add `whitespace-nowrap` to the columns that should never be squeezed.
To keep a whole table on one line per row and let it scroll instead, put the class on the table
itself. Cells inherit it:

```tsx
<DataTable caption="Cases" className="whitespace-nowrap" columns={columns} data={cases} />
```

If the table also stacks, scope it to the stack breakpoint, so long values can still wrap inside
the cards on narrow screens: `className="md:whitespace-nowrap"` for the default
`stackBreakpoint="md"` (`sm:` or `lg:` to match the others).

### Stacking into cards

With `responsive="stack"`, each row below `stackBreakpoint` becomes a card and every cell renders
its column header above its value. Resize your browser below 768px to watch these reflow — the
docs canvas is rendered at the page's own width.

<Canvas of={DataTableStories.Stacked} />

The label comes from each cell's `label` prop. USWDS uses a `data-label` attribute drawn with
`content: attr(data-label)`; here it is a real element, so it can hold any React content, and it
is only rendered while the table is stacked.

- `DataTable` fills `label` in from your column definitions (or `meta.stackedLabel`), so there is
  nothing to wire up.
- With the primitives, pass `label` on each body cell — usually its column header, or something
  more specific when that reads better on a card.

cells lose their column headers and the per-cell labels carry the meaning (see

record-style data; for wide numeric tables, `responsive="scroll"` keeps the grid intact.

### Cards with headings

`stackedStyle="headers"` promotes the first cell of each row to the card's heading instead of
labeling it like the rest — good when that first column identifies the record.

<Canvas of={DataTableStories.StackedHeaders} />

### Sticky header

`stickyHeader` keeps the column headers visible while the rows scroll. The table needs a scrolling
ancestor for that: the page itself, or a height-constrained container. Pair it with
`responsive="none"` so the default horizontal scroll wrapper doesn't become a non-scrolling sticky
context. USWDS advises against combining it with scrollable or stacked variants.

<Canvas of={DataTableStories.StickyHeader} />

## Empty values

A cell whose value is missing renders empty. Whether to show a placeholder instead, and what it
says, is up to your app: "—", "Not provided" and "None on file" each fit different fields. Do it in
the column's `cell` renderer, or in a helper your app's columns share:

```tsx
import type { DataTableColumnDef } from '@capitaltg/vero';

// A dash for sighted users, words for screen readers.
const EmptyValue = () => (
  <>
    <span aria-hidden="true">—</span>
    <span className="sr-only">No value</span>
  </>
);

// Only null, undefined and '' are empty: 0 and false are real values.
const orEmpty = (value: unknown) =>
  value == null || value === '' ? <EmptyValue /> : String(value);

const columns: DataTableColumnDef<Driver>[] = [
  { accessorKey: 'name', header: 'Name', meta: { isRowHeader: true } },
  { accessorKey: 'points', header: 'Points', cell: info => orEmpty(info.getValue()) },
  {
    accessorKey: 'altBirthDate',
    header: 'Alternate birth date',
    cell: info => orEmpty(info.getValue()),
  },
];
```

Two things to avoid:

- **A truthiness check** such as `value ? value : <EmptyValue />`. It turns a real `0` into a
  dash.
- **`aria-label` on a plain `<span>`.** ARIA doesn't allow a name on an element with no role, so
  screen readers may not announce it. Use visually hidden text, as above.

  intro="What Table and DataTable handle for you and what you need to add."
  title="Accessibility"

<DocsSubheading id="built-in">Built in</DocsSubheading>

- **It's a native HTML table**, so assistive technology gets table, row, header and cell roles,
  and screen readers' table navigation works.
- **Headers are associated with their cells.** `TableHead` defaults to `scope="col"`. In
  `DataTable`, spanning group headers get `scope="colgroup"` and the right `colSpan`, and the
  column marked `meta.isRowHeader` renders `<th scope="row">`. The empty corner cells that keep
  grouped columns aligned are `aria-hidden` cells, not empty headers.
- **The caption names the table.** `caption` renders a `<caption>`, which is the table's
  accessible name. `captionHidden` hides it visually but keeps it for screen readers. An
  `aria-label` or `aria-labelledby` you pass goes on the `<table>`.
- **Sortable headers are buttons** (`DataTable` with `enableSorting`). Each is a `<button>`
  inside the `<th>`, named by the header text; the arrow icons are hidden from screen readers.
  The `<th>` carries `aria-sort` (`ascending`, `descending` or `none`), and each change is
  announced through a polite live region, such as "Sorted by Role, ascending". The initial sort
  isn't announced on load.
- **Keyboard:** Tab reaches each sort button, and Enter or Space changes the sort.
- **A scrolling table is reachable by keyboard.** When the table overflows its container, the
  wrapper becomes a focusable `role="region"`, named by your `aria-label` or a plain-text
  `caption`, and the arrow keys scroll it. A table that fits adds no tab stop.
- **Focus is visible** on the sort buttons and the scroll region: a 3px ring outside a 3px white
  gap, 3.2:1 against the gap. In forced colors (Windows High Contrast) the ring becomes a
  system-colored outline.
- **Stacked tables keep their cell structure.** In Chromium, a stacked table is still a table
  with rows and cells, but the header row is hidden, so cells have no column headers. Each cell's
  label is part of its text instead, so a cell reads "Role Engineer". With
  `stackedStyle="headers"`, the first cell of each card is read without a label. We checked this
  in Chromium only; other browsers may expose stacked tables differently.
- **Contrast:** text is 13.8:1 on the header and striped-row background and 16.5:1 on the page
  background; the empty-state text is 5.1:1. Grid lines are 6.4:1 against the page, and the
  faded icon on unsorted columns 3.1:1 against the header.
- **Forced colors:** text, grid lines, sort icons and focus stay visible. Striping and header
  shading are dropped, as expected in that mode.
- **Tested with `vitest-axe`**: basic, grouped, row-group, style variant and stacked tables, and
  `DataTable` with a caption, sorting, grouped columns, stacking, card headings and the empty
  state.

<DocsSubheading id="your-responsibility">Your responsibility</DocsSubheading>

- **Give every table a name.** Prefer a visible `caption`. If a heading beside the table already
  names it, pass `captionHidden`, or use `aria-labelledby` pointing at the heading. If the
  caption isn't plain text (JSX), also pass `aria-label`: otherwise a table that scrolls gets a
  focusable wrapper with no name.
- **Mark one row header per row** when a column identifies the row: `meta.isRowHeader` in
  `DataTable`, or `<TableHead scope="row">` with the primitives.
- **With the primitives, write the header scopes yourself.** Spanning column headers need
  `scope="colgroup"` and a `colSpan`. Keep to two levels of headers; tables with more need `id`
  on each header and `headers` on each cell, which Vero doesn't add.
- **Use plain-text headers on sortable columns.** When a header is JSX, the sort announcement
  uses the column's id instead of its label
  ([#209](https://github.com/capitaltg/vero/issues/209)).
- **Expect single-column sorting.** Holding Shift while sorting adds a second sort column, but
  only the first is announced and both headers report a sort state
  ([#208](https://github.com/capitaltg/vero/issues/208)).
- **Label every cell when the table stacks.** `DataTable` fills in labels from the headers.
  With the primitives, pass `label` on each body cell. In a table with grouped columns, a card
  shows only the leaf header, so set `meta.stackedLabel` (or `label`) to include the group, such
  as "Q1 revenue". Don't stack a table people need to sort.
- **Check a sticky header against your layout.** In our check, focused links in the rows
  scrolled clear of the pinned header, but a fixed navbar or another sticky element on your page
  can still cover focused content.
- **Name links and buttons in cells for their row.** Write "Edit Ada Lovelace", or add visually
  hidden text, rather than a column of identical "Edit" links.
- **Show empty values in words for screen readers.** Use visually hidden text, as in
  [Empty values](#empty-values), not `aria-label` on a `<span>`.
- **Test it in your page.** Run the
  [USWDS table accessibility tests](https://designsystem.digital.gov/components/table/accessibility-tests/)
  on your own tables, including a screen reader pass, especially for stacked tables.

For an accessibility review, see
[all open accessibility issues for Table and DataTable](https://github.com/capitaltg/vero/issues?q=is%3Aopen+label%3Aa11y+%28in%3Atitle+Table+OR+in%3Atitle+DataTable%29).
